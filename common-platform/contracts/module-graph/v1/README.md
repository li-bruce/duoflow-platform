# 模块原子登记与业务节点映射 1.0

每个模块提供 `backend/module-graph.json`，将实际前后端组件与业务图关联。结构以同目录 JSON Schema 为准，引用及真实宿主检查由 `app/module_graph.py` 执行。模块套件 1.1.0 必须携带该附件，旧套件 1.0.0 继续按原协议检查。

## 登记内容

| 内容 | 必填信息 | 含义 |
| --- | --- | --- |
| 模块 | module_id、module_version、version | 所属模块、模块版本、业务图版本 |
| 后端原子 | id、capability、source | 对应唯一能力与真实源码位置；输入输出直接取能力声明 |
| 前端原子 | id、host、source、输入输出、状态初值、events | 对应共享组件或具名流程步骤，说明交互及状态效果 |
| 业务节点 | id、kind、title、description | 业务处理、状态、数据或判断节点 |
| 映射 | atom_id、node_id、role，可选 event_id | 一个原子可用于多个节点，动作可映射自己的业务位置 |
| 关系 | from、to、kind、title | 明确流程、调用、响应、数据或状态转换 |
| 状态机 | scope、owner_id、状态与转换 | 分开描述正式业务、组件显示和调用状态 |

后端能力的输入输出只有 manifest 一份来源。前端事件若绑定能力，其输入必须与实际组件动作一致，输出必须与真实能力一致。组件输入表示业务输入或对象投影，state_schema 表示个人填写内容；宿主提供的回调和认证上下文由 SDK 管理。

图只说明和观察实际行为。`state_effect` 是开发者可读的交互说明，不能当作授权、状态变更指令或已经成功执行的证据。运行时另以实例 ID 和调用 ID 区分每一次使用。

## 检查顺序

1. JSON 结构、版本、命名空间和唯一编号。
2. Schema 有效性、初始状态、动作输入输出。
3. 全部后端能力和全部前端步骤都有原子及节点映射。
4. 节点、边、事件和状态引用均存在；正式状态机与实际 workflow 一致。
5. 平台检查已安装宿主；模块 SDK 检查实际函数表。

套件 `module_kit.py check` 不导入供应商业务代码。Python `AtomBindings` 和 Node `createAtomBindings` 在服务启动时对照真正的 dispatch 表；握手不执行业务。源码位置是开发定位信息，不是平台下载或执行代码的地址。

## 修改与验证

先改真实组件或函数及对应契约，再同步图、测试和 Observer 映射。保留业务节点 ID，升级定义版本。组件单元测试核对实际交互和结果，业务测试独立读取模块存储，图映射测试核对两者对应关系。

现阶段附件和校验已实现；跨服务握手协商、运行同步和平台组合按 v0.02 工作表继续接入，不能仅凭本文件认为这些后续功能已经可用。
