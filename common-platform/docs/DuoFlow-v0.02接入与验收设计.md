# DuoFlow v0.02 接入与验收设计

当前状态：实施前的接口设计与验收清单。下文的新接口尚未实现，不能作为现有能力说明。总体分工见 [设计与依据](DuoFlow-v0.02设计与依据.md)，顺序工作表位于维护项目根目录。

## 1. 一份模块声明，区分五类身份

| 身份 | 表达的内容 | 生命周期 |
| --- | --- | --- |
| 原子定义 ID | 一个可复用的前端组件或后端功能 | 随定义版本固定 |
| 业务节点 ID | 这个功能在某个业务过程中的意义 | 随业务模型版本固定 |
| 组件实例 ID | 用户当前打开的具体组件 | 随个人办理实例存在 |
| 业务对象 ID | 模块保存的正式记录 | 由模块仓储管理 |
| 调用 ID | 一次有输入和结果的执行 | 每次调用独立；重试沿用同一请求身份 |

同一个组件可以对应不同业务节点。一次业务运行也可以多次使用同一个组件，分别产生组件实例和调用记录。节点映射必须明确列出，不能依靠中文标题、函数名称相似或画布位置推测。

新登记附件应携带：组件输入与输出、显示状态及初值、交互事件及反馈、允许调用的后端能力、业务节点和关系、公开业务流边界、数据接口、权限引用、版本和源文件位置。源文件定位只用于开发说明；不得作为可执行的远端代码地址。

后端功能复用 manifest 中已经校验的能力定义，避免再维护一套不一致的输入输出。前端组件继续由可信构建安装，登记不能让服务下发脚本执行。

## 2. 完整模块与部分业务怎样公开

平台只能组织模块主动公开的业务入口。一个模块可以有多个公开业务流；每个流声明自身入口、输入、输出、完成条件、需要的权限与数据，以及在完整内部图中的节点范围。

需要复用一部分业务时，模块为这一部分提供具名入口和边界。例如，模块内部有“整理、检查、确认”三段，可以公开完整处理，也可以另行公开“检查”。后者仍调用模块自己的检查函数，保留必要的状态和权限判断。平台不能从内部图任意剪出几个函数就执行。

公开流的边界说明需要回答：

1. 接受哪些字段或对象引用，哪些状态可以开始。
2. 由哪个真实接口受理，页面与对话使用哪个已安装组件。
3. 返回哪些字段，哪些结果代表完成、等待或失败。
4. 等待之后如何继续、查询和确认，重复请求如何识别。
5. 哪些内部节点可公开观察，哪些内容只留在模块。

## 3. 接入检查的责任

保留现有七项验收，并在相应阶段核对新附件。旧 registration 1.0 不增加隐含字段；新功能使用显式协议版本和能力协商。旧模块继续独立调用，只有具备完整新声明的模块才能进入组合目录。

| 检查位置 | 平台检查 | 模块主动确认 |
| --- | --- | --- |
| 能力声明 | 模块身份、版本、能力命名空间、输入输出 | 本地 manifest 与平台收到的内容完全一致 |
| 业务声明 | ID 唯一性、引用完整、前后端映射、公开流边界 | 声明对应实际函数表及本地定义 |
| 权限与数据 | 每项公开动作有权限对应；数据操作有合适的查询或命令 | 对象事实从模块仓储取得；业务权限判断可用 |
| 接口认证 | 无凭据和错误凭据均拒绝 | 先验证平台连接，再解析业务调用 |
| 服务健康 | 确认当前连接可用 | 返回当前服务身份和健康结果 |
| 握手 | 完整合同、唯一请求标识、版本支持 | 比较完整内容，检查真实绑定后返回确认 |
| 两端宿主 | 组件和流程已安装、版本一致、动作和 Schema 相容 | 前后端契约与已声明的公开流对应 |
| 运行同步 | 只接受当前连接及受理调用的有界事件 | 发送实际事件；观察故障不改变业务结果 |

接入成功只代表合同与接口通过检查，不授予任何用户业务权限。更新声明、连接或宿主依赖后，旧验收结果必须失效并重新检查。

## 4. 组合业务的执行边界

组合保存公开流版本、顺序和明确字段对应。运行保存每一步的输入身份、调用编号、当前情况和回执。定义与运行分离；修改定义不能改变历史运行的解释。

初始实现优先支持明确的顺序连接和等待办理。循环、并行、补偿和任意脚本转换在支持前必须拒绝，不能在图上显示后按另一套含义执行。一个业务流内部仍可使用模块自身的成熟逻辑。

| 情况 | 必须保持的行为 |
| --- | --- |
| 前一步完成 | 校验实际输出及字段对应，然后准备下一步 |
| 输入缺项 | 保持等待，显示所缺字段，业务尚未执行 |
| 权限缺项或撤销 | 拒绝下一次调用，不写入目标模块 |
| 服务离线 | 保留已经完成的回执，明确当前不可用 |
| 超时且结果未知 | 显示结果待确认，不能推断模块没有保存 |
| 重复点击或页面刷新 | 读取现有运行；相同请求身份不重复产生业务效果 |
| 连接、定义或版本变化 | 旧运行拒绝继续使用变化后的接口，要求重新核对 |
| 观察接口故障 | 业务继续按原逻辑执行，图明确显示缺失记录 |

字段对应只允许选取已声明的来源和目标，不能执行表达式。数据保留在模块，平台只保存执行所需的有限输入与回执。跨模块使用数据时，重新核对来源可读和目标可写；预检结果不能代替执行时检查。

## 5. 身份与角色的组合

平台提供统一用户身份；模块提供业务权限名称、角色模板、对象范围字段和业务限制。已有 access v1 的范围授权继续作为基础。

组合角色是管理员明确组织的一组模块角色及范围对应。模块甲的“审核人”与模块乙的“审核人”可能有不同权限，不能因为同名自动合并。角色组合必须能预览将涉及的模块、权限和范围，并保留逐项授予与撤销记录。

注册、创建组合和查看业务图均不能自动扩权。对象范围来自可信存储，不能把用户填写的组织或项目字段直接作为获准范围。每条授权内部各条件同时成立；不同授权之间不能拆开拼接出更大的范围。

## 6. 独立验证清单

预期由需求和真实存储定义，不能从图中复制一份相同结果作为测试答案。

| 层次 | 正例 | 反例与边界 | 独立依据 |
| --- | --- | --- | --- |
| 原子声明 | 前后端定义、Schema、节点和动作完整 | 重复 ID、无目标引用、错误状态初值、缺失函数 | 实际组件注册表、函数表 |
| 组件交互 | 输入、事件、等待、反馈、恢复 | 过期实例、重复提交、无权限动作 | 真实组件测试和后端回执 |
| 模块状态 | 页面与对话操作同一对象 | 非法转换、修订冲突、撤权后提交 | 模块数据库中的对象和版本 |
| 公开业务流 | 多个入口与部分业务均可调用 | 边界缺失、私有节点被直接调用、版本不符 | 模块独立场景测试 |
| 握手 | 两端确认同一合同及真实绑定 | 内容不符、缺接口、凭据错误、依赖未安装 | 实际 HTTP 请求和独立模块 |
| 数据连接 | 已声明来源正确传入目标 | 类型不符、缺字段、越范围、来源读取被撤销 | 来源读取与目标存储分别核对 |
| 组合运行 | 完成步骤、等待、继续、恢复 | 重复点击、服务错误、超时、升级中途发生 | 两个模块数据库与平台逐步回执 |
| 角色组合 | 显式授予、限定范围、逐项撤销 | 同名自动扩权、跨授权拼接、注册默认授权 | 当前授权表和两端真实决定 |
| 运行同步 | 前后调用与实例关联、重连 | 重复、乱序、缺口、过期、他人记录、错误连接 | 实际调用与模块状态读数 |
| 观察隔离 | 开启、关闭、传输失败、队列满时业务一致 | 图自身操作制造业务事件 | 独立业务结果与写入次数 |

后续新会话验收只接收候选仓库、Skill 和明确的两项 demo 需求，记录问题、修复与重测。开发者自测、独立会话测试、外部模型测试和人工体验分别记录。
