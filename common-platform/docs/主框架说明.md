# 主框架：架构、功能与使用要求

技术监控已拆成独立服务：接收模块实例心跳和负载、执行健康探测并聚合；主API只以5秒周期读取有界快照。独立进程和SQLite分别启停，监控故障不制造全模块离线；业务授权、正式状态和业务观察票据保持原边界。设计、启动与报告协议见[独立监控服务](独立监控服务设计.md)。

模块AI服务支持声明和交互式配置：管理员在模型连接界面为每项服务明确选择平台模型连接或模块自有API，平台Key由中央broker使用，自有Key由模块私密保存；控制管理与业务授权分别核验。详细操作、调用顺序和边界见[模块AI服务与配置](模块AI服务与配置.md)。

v0.02：新增原子组件登记、公开业务流边界、实际运行观察与 1.1 接入确认。源码位置、字段和使用关系见 [原子组件与公开业务流](原子组件与公开业务流.md)。旧 1.0 接入仍兼容；顺序组合、明确字段连接、组合角色与整体运行图见 [组合业务运行与角色](组合业务运行与角色.md)。对应发布范围与实测边界见仓库根 VALIDATION.md。

主框架负责统一身份、用户授权、模块服务管理、能力调用、页面与对话、私人流程和执行记录。业务模块通过统一协议提供功能；业务数据、正式状态和专业规则留在业务模块中。

平台已提供独立顺序组合执行器。登记入口后，由使用者明确选择业务、连接数据、保存版本并开始；平台按确认要求和模块正式状态继续推进。

跨模块固定来源读取提供可选 [source-reads 1.0](../contracts/access/v1/source-reads.md)。目标服务保留自己的业务适配器，用当前票据请求平台检查两端并读取已登记源对象；源凭据不交给目标，固定版本与当前权限逐次核对。该回调不替代源字段投影、用途规则或业务交付审批。

权限目录仍逐次读取当前授权、有效期与角色定义。固定 Casbin 模型中的每条完整授权各有独立域；目录只需找到一个允许域便停止，正式对象判断继续检查全部必要事实，不缓存旧允许结论。细粒度字段授权不会再让每个无关目录能力遍历所有授权域。

## 1. 代码结构

| 位置 | 职责 |
| --- | --- |
| `app/main.py` | 装配依赖、路由、后台任务和应用生命周期 |
| `app/registry.py`、`module_contract.py`、`workspace_contract.py` | 能力、两端入口和调用结果校验 |
| `app/runtime.py` | 调用、重新授权、发布与运行记录；不承担具体业务计算 |
| `app/remote_services.py` | 管理固定服务地址与凭据、发现清单、接口检查、原子保存验收结果 |
| `app/registration_contract.py` | 接入声明、握手确认、验收记录的结构和引用规则；不连接服务、不授予权限 |
| `app/remote_routes.py` | 管理员接入接口、请求修订与权限复核 |
| `app/identity.py`、`security.py`、`access_control.py`、`access_bridge.py` | 用户身份、会话、范围授权及远程决策 |
| `app/workflows.py`、`workflow_transport.py`、`interactions.py` | 私人流程、对象适配和共享组件 |
| `app/conversation.py`、`agent_engine.py` | 对话、明确流程入口和个人导航 |
| `app/service_monitor.py` | 独立心跳；心跳恢复不会自动发布模块 |
| `app/db.py`、`module_state.py` | 平台自己的持久记录和模块启停修订 |
| `web/src/RemoteServices.tsx` | 服务连接、声明预览、七项接入结果与发布入口 |
| `web/src/workflows/`、`interactions/` | 页面与对话共用的宿主 |
| `contracts/` | 可携带、机器可读的公共协议 |

模块框架位于 `templates/module-kit/`，它是可携带 SDK 和模板，不是另一台主框架服务器。主框架不导入远程业务源码，也不根据远程清单加载脚本、页面代码或数据库凭据。

## 2. 接入成功的标准

保存连接只登记地址；发现能力只形成预览。以下七项全部通过，形成当前连接修订的验收记录后，才允许启用发布。

| 检查 | 实际检查内容 |
| --- | --- |
| 能力声明与输入输出 | 重新获取清单；核对身份、版本、能力唯一性、输入输出 Schema、两端呈现；必须与预览相同 |
| 数据、流程与权限声明 | 校验 registration v1；检查命名、公开对象操作、能力引用、权限完整映射和所需流程 |
| 接口身份验证 | 无凭据和错误凭据访问全部声明接口时必须拒绝 |
| 服务健康状态 | 必须明确健康，互相矛盾的健康字段不能通过 |
| 无效请求拒绝 | 携带正确连接凭据，向调用、握手及声明的对象接口发送空请求；必须在业务执行前返回 400 或 422 |
| 模块主动确认 | 平台发送完整声明、支持内容、一次性随机编号和内容摘要；模块核对本地完整声明、实际函数绑定与 Schema 后确认 |
| 平台依赖 | 权限附件已注册且一致；组件/流程已安装且版本匹配；不存在模块和能力名称冲突 |

检查按顺序执行；失败后其余项目标为尚未检查，不把没有执行的项目算通过。报告不保存远程正文、用户数据或凭据。连接修改会清除验收。已发布服务重新验收失败时立即停用，并改变连接修订，使旧调用失效。

验收后五分钟内可发起发布。发布时再次核对平台权限和呈现依赖；启用/停用会更新连接修订，但不会延长验收时间。已启用服务由独立心跳持续观察，心跳不代替接入验收。

旧配置中没有验收记录的服务保留预览，启动时不会自动进入可调用目录。旧 manifest 1.0/1.1 适配器也须补齐本标准握手；范围授权仍要求 manifest 1.2 / invoke 1.1。新模块直接使用现代协议。

## 3. 管理员使用步骤

1. 在服务接入页保存服务地址、私有连接凭据和超时。HTTP 只接受回环地址；其他机器使用 HTTPS。
2. 发现并核对能力，保持未发布。
3. 在受控发布中安装声明需要的共享组件和流程，完成前端构建、重启；平台不自动安装远端代码。
4. 注册模块的权限附件。它描述权限规则，不创建任何用户授权。
5. 点击“检查模块接入”。逐项修复未通过内容，再完整检查。
6. 七项全部通过后启用发布，再向具体用户分配业务权限和范围。
7. 用合成业务验证正常、拒绝、冲突、重试、刷新和分支，再单独验收业务功能。

管理接口位于 `/api/v1/remote-services`。保存、发现、接入检查、启停均需要当前管理员身份和防伪请求头；网络等待后重新验证管理员身份。接入检查为 `POST /{service_id}/admission`，正文 `{"expected_revision": 1}`。返回服务信息中的 `admission` 是逐项报告，`registration` 是已验证的公开内容；失败报告也正常返回，调用方必须读取 `admission.passed`。

接入检查不调用有效业务命令，不生成业务账号、授权、记录或文件。模块必须先验证请求包络再执行业务。接入成功证明协议与声明依赖相符，不证明专业算法正确、真实业务权限设计充分或用户操作已经验收。

## 4. 权限与存储规则

- 连接凭据识别主框架与服务连接；实际用户身份由平台生成。两者不能互相代替。
- 平台保存真实授权；模块根据自己仓库中的组织、项目、作者、状态等事实请求判断。浏览器输入不能当成授权事实。
- 主框架通过公开业务操作读取和修改数据，不连接模块数据库执行任意增删改查。
- 模块状态、个人流程位置、后台调用状态分别保存。刷新和个人分支不会重新执行业务写入。
- 接入声明允许登记数据类型和模块业务步骤；它不引入自动跨模块执行、通用字段授权或分布式回滚。

## 5. 安装、运行和验证

在本独立项目内创建 `.venv` 和前端依赖，使用锁定依赖及 Node 24。具体安装与身份隔离要求见框架 [README](../README.md)；源码包中的入口见 `START-HERE.md`。只启动本项目 8030，不能使用原 8020 的运行目录或凭据。

在 `common-platform` 执行，测试数据必须独立：

```powershell
New-Item -ItemType Directory -Force ..\work\checks | Out-Null
$env:PLATFORM_DATA_DIR = (Join-Path (Get-Location) '..\work\checks\data')
.\.venv\Scripts\python.exe -m pytest -q --basetemp ..\work\checks\pytest-new
.\.venv\Scripts\python.exe scripts/build_module_developer_prompt.py --check
# web 内 npm test、npm run build；使用 Node 24
.\.venv\Scripts\python.exe scripts/build_handbooks.py --check
```

验收重点为 `tests/test_registration_admission.py`、`test_remote_services.py`、`test_module_kit.py` 和前端 `RemoteServices.test.tsx`。真实 Node 参考包联调覆盖中央授权、对象写入与恢复；真实模型、外部业务数据、生产身份和多进程高可用另行验证。

## 6. 维护要求

公共变更先更新 Schema、校验器、SDK、模板及测试，再更新文档、源提示词并重建生成物。业务变更优先留在模块；主框架仅接受通用接口改进。关键代码注释解释身份来源、并发修订、失败处理与数据归属，不用逐行注释复述代码。

更详细的标准见 [模块接入标准](../contracts/registration/v1/README.md)，模块侧架构见 [模块框架说明](模块框架说明.md)，完整代码地图见 [通用框架架构与代码地图](通用框架架构与代码地图.md)。

浏览器界面 presence 心跳仅更新观察旁路，检查当前身份、实例归属、授权指纹、定义和个人修订。它不调用业务对象读取，不采用后台回执，也不改变个人步骤；主动调试查看正式状态时仍通过完整授权读取。界面在线、服务健康、正式状态和 Run 结果分别判断。

## 并行状态机协同

平台新增独立业务协同中心，连接多个同时办理的模块，管理状态汇集、公开申请和通知/同步订阅。主框架通过管理页查看汇总和处理申请；各模块仍执行自身正式状态机。可靠事件使用同事务Outbox/Inbox、租约及确认，示例、架构与操作见[并行业务状态协同](并行业务状态协同.md)。
