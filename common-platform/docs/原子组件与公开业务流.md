# 原子组件与公开业务流

模块的公开结构分为三层：可调用的原子能力、组成业务的节点与状态，以及供平台使用的明确业务入口。业务代码仍决定实际处理过程，业务图用于关联、观察和测试。

## 源码位置

| 路径 | 职责 |
| --- | --- |
| app/module_graph.py | 校验原子、事件、状态和实际共享宿主的一致性 |
| app/flow_exports.py | 校验公开业务边界，并从真实能力解析输入输出与权限 |
| app/module_catalog.py | 从已安装或已验收模块构建当前可用业务目录 |
| app/atomic_instances.py | 把实际组件实例、保存的局部状态及界面观察关联到原子 |
| app/runtime_observation.py | 单次运行观察凭据、握手回调、去重、授权读取与独立保存 |
| templates/module-kit/sdk | Python、Node 和前端原子绑定与观察支持 |
| scripts/module_graph_template.py | 从实际能力和共享组件生成可编辑的原子登记初稿 |
| scripts/flow_exports_template.py | 从实际能力和共享流程生成可编辑的公开入口初稿 |

## 一个组件如何找到业务位置

`backend/module-graph.json` 中的 atom ID 标识组件定义，host 指向实际 interaction 或 workflow 的具体步骤。mappings 将原子及其事件映射到一个或多个业务节点；edges 描述顺序、调用、响应、数据和状态转换关系。同一个业务节点可以由多个界面展示，同一个组件也可以服务多个业务位置。

前端登记输入、输出、局部状态、事件和交互效果。事件涉及业务调用时，能力编号、版本和输入输出必须与真实宿主一致。后端原子的输入输出直接取 manifest，避免两份声明失配。每个实际能力和共享组件都必须登记，漏项、未知引用或版本漂移会被检查器拒绝。

组件实例使用现有共享宿主的实例编号；流程步骤在实例编号后附步骤 ID。运行观察另用 request_id 和 call_id。正式业务状态取模块 projection，个人导航取 cursor，执行状态取 Run，浏览器报告单独标注为界面状态。

## 一个模块如何公开多个业务入口

`backend/flow-exports.json` 可以声明多个入口。一次功能对应 capability；需要用户分步办理的业务对应 workflow，并给出 completed_states。部分业务单独定义入口和完成边界。完整业务和部分业务可以复用相同内部实现，平台只调用模块声明的边界。

公开入口列明数据对象与操作，输入输出从真实接口解析。入口权限应与实际读取或调用一致；后续动作分别检查各自权限和对象事实。角色模板帮助使用者理解职责，实际授权仍按用户、角色模板和范围分别建立。

## 页面与对话

页面和对话继续使用相同的 InteractionHost 或 FlowHost。对话可通过 `/business <公开入口编号>` 找到入口，先打开对应共享组件或参数表，再由用户完成业务操作。已有 `/flow`、`/component` 和业务关键词引导继续使用原入口。实际组件实例观察会关联同一组原子与业务节点。

## 检查与边界

模块可用 SDK 的 `graph_testing.py` / `graph-testing.mjs` 检查原子实际输入输出，以及业务函数执行前后读到的对象状态。测试程序负责调用真实接口，辅助函数只核对登记内容。这样改动业务代码或状态图后，原有场景会及时指出两者之间的偏差。权限拒绝、事务写入、修订及幂等效果仍由独立场景断言验证。

套件静态检查核对契约、实际宿主与引用，SDK 在服务启动时核对真实函数表。接入 1.1 再核对完整附件，并要求模块主动确认运行同步回调。以上检查分别证明结构、函数绑定和接口互通；业务正确性由模块场景、对象权限与端到端测试验证。

Observer 映射版本 2 覆盖全部公开原子、节点和业务流。module-graph.json 和 flow-exports.json 都要纳入持续同步输入。内部完整业务网与平台公开图保持明确映射，不能用一个较小的公开图冒充完整实现覆盖。

跨模块顺序组合和交互式编辑器已实现，见 [组合业务运行与角色](组合业务运行与角色.md)；两个 demo 的整体验收仍按根工作表推进。本阶段未执行真实外部模型调用；对话检查使用确定性入口与现有 Agent 回归。
