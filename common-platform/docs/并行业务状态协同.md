# 并行业务状态机与消息协同

DuoFlow 的四个业务模块可以同时工作：汇交组提交新数据，挖掘组查询已有资源，科研人员处理申请，治理人员整理和审批另一批数据。平台把相互有关的变化送给需要知道的模块。

## 谁做什么

| 部分 | 职责 | 例子 |
| --- | --- | --- |
| 模块自己的状态机 | 检查业务条件，保存对象状态和修订 | 一批数据由待公开变为公开 |
| 独立业务协同中心 | 汇集最新状态，管理公开申请、订阅与消息投递 | 数据公开后同时通知挖掘和科研 |
| 主框架 | 管理参与模块、订阅和审批，展示中心汇总 | 管理员在“业务协同”页处理申请 |
| 独立技术监控中心 | 汇总服务健康、CPU、内存、负载 | 判断模块是否正常运行 |

业务协同中心与技术监控中心是两个进程、两份存储。模块把业务事件直接交给协同中心，主框架每次读取有界汇总；原顺序组合用于明确按先后安排的单条办理流程。

## 一次公开怎样影响多个正在工作的模块

1. 来源模块把对象改为待公开，并在同一事务写入 `publication.requested` 待发送事件。
2. 协同中心接收事件，登记公开申请。其他模块继续自己的工作。
3. 平台管理员在“业务协同”页选择同意或退回。中心保存决定，并把处理结果送回来源模块。
4. 来源模块核对申请编号、对象修订和自身业务条件，在本地事务中执行公开，同时写入 `resource.published` 事件。
5. 中心校验这次公开对应已批准的申请版本，为每条匹配订阅建立独立消息。
6. 挖掘模块收到“同步”，刷新来源索引；科研模块收到“告知”，记录通知。需要数据正文时，各模块通过来源公开接口和当前授权读取。
7. 接收模块把自己的处理和 Inbox 记录一起提交，再向中心确认。暂时离线的模块恢复后继续领取待处理消息。

申请修改后的新版本需要新的审批。中心中的“已批准”表示该次申请的决定；正式公开状态来自来源模块实际保存的结果。

## 并发、顺序与恢复

每个模块、每个对象都有自己的修订。中心保存每个对象的新状态，各对象之间可以同时推进。同一对象的消息按先后处理，避免较旧变化覆盖新结果。

模块 Outbox 与业务记录在同一事务提交：业务回滚时事件也回滚，网络故障后保留待发送事件，重启继续发送。中心按事件编号去重，事件编号相同但内容不同会报告冲突。

一个事件向多个模块分发时，每个接收者都有自己的投递、租约和确认。某个消费者失败，其他消费者照常处理。消费者把业务处理和 Inbox 一起提交；确认丢失后重新领取，只补确认，已经提交的处理保持一次。传输语义是至少一次投递，模块通过 Inbox 实现幂等处理。

中心只携带状态、对象引用、版本与范围；数据正文由原模块管理。自动执行外部业务动作时，模块还需在自己的处理函数中检查当前执行身份、授权和业务条件。SQLite SDK 的原子性覆盖同一数据库内的写入；外部 HTTP、文件、邮件等副作用应继续通过目标系统的幂等接口或目标 Outbox 执行。

## 模块怎样声明和接线

注册声明的可选 `coordination` 描述：本模块拥有的状态机和对象类型、可以发送的事件、愿意接收的来源事件与处理方式。平台对模块 ID、业务状态集合、对象引用和两侧订阅约定做一致校验。

机器可读协议在 `contracts/coordination/v1/`，Node/Python SDK 在 `templates/module-kit/sdk/`，可运行公开申请示例在 `templates/module-kit/examples/coordination/`。

Node 接线顺序：`initializeCoordination(db)` → 业务事务中的 `enqueue(db,event)` → 提交后的 `client.relay(db)` → `client.pull()` → `client.consume(db,delivery,handler)`。Python 对应 `initialize`、`enqueue`、`relay`、`pull`、`consume`。处理函数在同库短事务中修改自己的业务数据。

workflow-node 蓝图通过 `DUOFLOW_COORDINATION_CONFIG_FILE` 读取本模块连接；范围来自模块可信项目配置，来源列表来自接入声明。公开审批处理由具体业务实现，可参考公开申请示例；普通业务审批与资源公开分别建模。

## 启动与使用

从 `common-platform` 启动独立中心（示例中的路径均属于当前工程）：

```powershell
.\.venv\Scripts\python.exe scripts/coordination_service.py start --platform-data .\data\local --data-directory .\data\coordination-local --port 8033
```

启动主框架后，管理员进入 `/#coordination`，查看业务状态、处理公开申请，在“配置参与模块与订阅关系”中选择模块，填写来源、事件、接收模块、机构/项目与告知/同步方式。

模块凭据只导出到本工程忽略的 `work/`，不经过浏览器：

```powershell
.\.venv\Scripts\python.exe scripts/coordination_service.py credentials --platform-data .\data\local --data-directory .\data\coordination-local --service-id demo.source --output ..\work\demo-source-coordination.json
```

将该私有文件路径交给来源模块的 `DUOFLOW_COORDINATION_CONFIG_FILE`。配置生效前，两侧须安装本次 SDK 与协同声明。

主框架会复核已配置模块的当前接入修订、声明和发布状态；失配时向中心停用绑定并取消未处理投递。重新接入后由管理员再次确认配置。中心配置、模块令牌与消费者租约分别校验。

停止中心使用同一脚本 `stop --data-directory ...`，按解释器、命令、创建时间核验进程身份。中心停止期间，模块保留 Outbox，已成功提交的业务继续保存。

## 验证

`tests/test_coordination_service.py` 覆盖事务、幂等、审批、范围、并发租约、配置撤销、重启与脱敏。`tests/test_coordination_registration.py` 对平台及两侧注册 SDK 做一致性检查。`scripts/coordination_acceptance.py` 使用真实 HTTP 中心与四个独立模块进程/SQLite，覆盖并行工作、审批、三目标通知/同步、离线补收、重启和两种确认丢失。

这组进程属于框架隔离合成服务验收，报告中的耗时用于说明这次运行结果。现有业务模块采用新能力时，需要把自己的事务和消息处理接入本次 SDK。
