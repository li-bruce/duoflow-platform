# 模块公开与业务组织：现状和建议

日期：2026-10-22。源码基线：99ae7c5。本次是架构分析、隔离边界验证和讲解页面更新，没有新增组合执行器。

## 结论

总框架的核心定位是：管理微服务，统一身份和公共功能，让模块公开业务行为、数据与接口，再把这些内容组织成跨模块业务。组合后的业务继续同时使用页面和对话。

现有代码已经具备“统一登记、统一调用、统一身份、共享呈现，以及带明确参数的后续动作”这部分基础；尚不具备完整的“任意跨模块业务自由组织”。缺口集中在组合定义、数据连接、多对象关系、组合执行记录和组合级恢复。这是能力分层的判断，不采用没有分母的完成百分比。

## 当前支持程度

| 维度 | 当前具备 | 限制和依据 |
| --- | --- | --- |
| 微服务管理 | 连接登记、功能发现、预览、启用停用、版本与健康检测 | 管理接入与发布，不是启动、部署或扩容远端进程。`app/remote_services.py`、`module_state.py`、`service_monitor.py` |
| 身份与权限 | 本地账号会话、统一可信身份、模块范围权限、远端短时中央判断 | 同一身份不等于同一权限。目标模块必须单独判断数据范围；外部统一登录和长任务授权委派未完整实现。`security.py`、`access_control.py`、`access_bridge.py` |
| 业务行为公开 | 功能 ID/版本、query/command、输入输出 Schema、执行方式、两种呈现和权限 | 描述格式和调用，不自动描述“哪个状态变化允许调用、改变哪些对象、能否补偿”等完整业务语义。`registry.py`、`module_contract.py` |
| 数据公开 | 输入输出数据、结果资源、对象目录/读取/详情、类型/编号/版本/状态/允许动作 | 没有独立的跨模块数据目录、含义字典或通用关系查询。一份 workflow 只有一个主 provider 和当前 object_ref。related_object_types 仍经同一 provider 读取。`workflows.py`、`workflow_transport.py`、`contracts/workflows/v1/definition.schema.json` |
| 接口对接 | 原生函数调用、受管理的 HTTP manifest/health/invoke、对象/文件/任务接口 | 不自动接通任意 REST URL；已有系统仍需适配统一请求与身份。`runtime.py`、`remote_services.py`、`workflow_transport.py` |
| 结果交给下一模块 | workspace.actions 指定目标功能和明确 input；预填下一表单，提交后进入统一执行 | 目标功能可以属于别的模块，且重新检查权限；只保留目标输入声明里的字段，不解释字段含义、不自动变换类型、不自动执行。`Runtime.refresh_workspace`、`WorkspaceView.ActionList` |
| 业务组织 | 可安装共享组件和步骤定义，动作引用明确功能；技能可按已成功结果推进 | skills 仅允许本模块 capabilities；workflow 未提供多 provider、跨步骤 input_bindings 或组合结果存储。动作可以写别的功能编号，不代表跨模块对象和数据管理已经完成。`normalize_skills`、`Workflows.action` |
| 页面与对话 | 同一组件接口、同一对象读取、个人草稿与步骤恢复 | 单模块机制已经存在；独立组合定义与组合运行记录尚不存在，不能声称有完整组合业务的双形态宿主。`web/src/workflows/`、`interactions/` |
| 失败与恢复 | 调用级重复请求检查、本地事务、后台执行记录、模块健康和版本核对 | 无组合级步骤账本、通用补偿与跨服务事务。远端超时结果未知，不能自动重做。各模块正式状态仍分别保存。`runtime.py`、`remote_services.py` |

## 隔离验证

`tests/test_composition_boundaries.py` 使用临时数据库、框架实验室与另一个合成原生模块，6 项检查通过：

1. 全局目录可同时公开两个模块；来源模块的结果动作可以明确指向第二模块。
2. 准备动作不执行处理函数；明确调用后，目标函数收到同一当前身份和显式传入引用。
3. 多余预填字段被过滤；目标无权限时动作被移除，直接调用也被拒绝。
4. 同模块技能定义引用别的模块功能被 normalize_skills 拒绝。
5. 当前 workflow Schema 不接受 providers 或 input_bindings 字段。
6. 输入类型不匹配时拒绝调用，不自动把对象转换成字符串。

参数化 Schema 检查计两项，合计 6 项测试。仅证明上述机制和限制；不是三个真实微服务的组合业务验收。现有远程测试、单模块流程测试提供各自范围的证据。

## 应怎样补齐

### 1. 模块提供可组合的业务说明

在现有功能说明上补充业务语义，仍保留现行 manifest/invoke 的兼容性。模块至少公开：

- 行为：稳定功能 ID/版本、查询或修改、输入输出、涉及的对象类型、前置条件、影响、是否需要确认、重复请求和失败查询方式。
- 数据：对象类型、字段含义、读取接口、对象身份和版本、关联引用、数据范围、分页或文件引用。公开可授权的数据读取，不公开数据库连接和任意表访问。
- 接口：用已有受管理连接和认证传递；外部系统通过适配器转换。接口地址和凭据留在服务端，组合定义引用已登记功能，不接受浏览器任意 URL。
- 界面：查询、编辑、处理、结果组件，页面与对话共用。既有模块业务逻辑和正式状态仍归模块所有。

这些是建议的扩展内容，不是可直接填写到当前 Schema 的新增字段。应先定契约再实现校验和兼容转换。

### 2. 增加独立的组合定义

组合属于总框架的业务组织层，不属于任意一个模块的私有技能。一个定义包含组合 ID/版本、步骤、目标功能及版本、前置步骤、明确的数据连接、涉及的对象引用、人工确认、完成条件与失败处理。

先支持固定顺序和明确字段连接。例如 A 的 output.document_id 对应 B 的 input.source_id，必须说明来源类型、版本和授权，不靠同名字段自动猜测。校验不存在的功能、缺失必填输入、格式不符、循环依赖和未声明输出。条件分支可后续扩展，不立即引入任意脚本。

### 3. 增加组合运行记录

每次办理产生一个组合运行编号，保存冻结的定义版本、各步骤状态、使用的对象引用与版本、请求编号、输入摘要及调用回执。主框架安排步骤，每次执行仍重新确认当前身份、目标功能权限与对象范围。

步骤成功才向后传递明确结果；失败停止后续。重试同一步沿用相应请求标识并检查原输入。远端超时先查询回执或人工确认，不能用新编号盲目再做一次。A 成功、B 失败时保留 A 的真实结果；回退业务必须有模块提供的明确反向动作，不能假装一次数据库回滚能够撤销多个服务。

### 4. 组合业务继续共用两种界面

页面可以同时显示各步骤和各模块结果；对话聚焦当前步骤。两者读取同一组合定义、同一组合运行编号，使用相同模块组件和动作。切换入口不创建第二条组合；对话分支复制个人视图，正式动作不重放。

## 建议落地顺序

1. 固化模块公开说明与组合定义；增加校验器和版本规则，保留旧模块正常使用。
2. 用三个职责不同、独立保存数据的模块完成固定顺序的组合。先查询、处理、确认，不要求模型参与，不做自动补偿。
3. 增加组合运行记录与页面/对话共用界面；完成重复提交、失败后继续、权限变更、版本冲突和超时确认。
4. 有真实需求后再增加条件分支、人工等待、并行步骤、文件与长任务，以及模块提供的补偿动作。

不先做拖拽编辑器。先有能验证的定义与执行器，界面才有真实规则可以操作。

## 验收门槛

三个实际模块分别保存自己的记录，使用同一用户身份完成 A → B → C；B 接收明确的 A 引用与版本，C 接收明确的 B 输出。页面做到 B 后能在对话继续，同一组合编号保持不变。

必须验证：A 有权而 B 无权时不能继续；A 输出缺失或版本变化时不执行 B；B 离线或超时不执行 C；重复请求不产生第二条业务记录；刷新恢复同一步；分支不重放；A 成功 B 失败时 A 的事实保持；目标模块仍能拒绝对象范围不符的输入。通用执行器、双形态界面和每个模块业务规则分别验收。
