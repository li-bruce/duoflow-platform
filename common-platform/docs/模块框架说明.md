# 模块框架：架构、功能与接入要求

使用AI的模块应在可选 `registration.ai_services` 声明稳定服务、关联能力和支持来源，并接入同批Python/Node AIServiceManager。独立使用自有API，接入后按平台管理员明确配置的来源调用，调用前后和最终提交前核验权限与配置修订。接口、示例与私有存储规则见[模块AI服务与配置](模块AI服务与配置.md)。

v0.02：新增原子组件登记、公开业务流边界、实际运行观察与 1.1 接入确认。源码位置、字段和使用关系见 [原子组件与公开业务流](原子组件与公开业务流.md)。旧 1.0 接入仍兼容；顺序组合、明确字段连接、组合角色与整体运行图见 [组合业务运行与角色](组合业务运行与角色.md)。对应发布范围与实测边界见仓库根 VALIDATION.md。

模块框架是一套可携带的协议、服务端 SDK、模板和检查工具。它帮助独立业务服务按统一规则公开功能、数据和业务步骤，接受主框架管理。它不替代业务系统，也不另建用户身份、授权中心或对话系统。

## 1. 结构与分工

| 位置 | 内容 |
| --- | --- |
| `templates/module-kit/blueprints/tool-python` | 受信任的进程内 Python 工具模板，共享组件与纯业务函数分开 |
| `templates/module-kit/blueprints/workflow-node` | 独立 HTTP 服务，包含对象、状态、修订、事务和持久回执示例 |
| `templates/module-kit/sdk/node/runtime.mjs` | 固定路由、连接认证、请求校验、真实函数分派和输出校验 |
| `templates/module-kit/sdk/node/registration.mjs` | 服务启动时核对函数覆盖；握手时主动核对双方完整声明 |
| `templates/module-kit/sdk/node/access-client.mjs` | 向配置的中央地址请求范围权限判断 |
| `templates/module-kit/sdk/node/store.mjs` | 单进程 SQLite 事务、回执与分页游标参考 |
| `templates/module-kit/sdk/python/module_kit.py` | 原生工具上下文及权限、输入输出边界 |
| `templates/module-kit/sdk/python/registration.py` | 已有 Python HTTP 服务可携带的注册确认器 |
| `templates/module-kit/sdk/python/remote_access.py` | Python 服务的中央权限决策客户端 |
| `scripts/module_kit.py` | 生成和离线检查；不启动服务、不安装、不发布、不授予权限 |
| `contracts/registration/v1/` | 公开内容、握手请求、确认回应的严格 Schema |

业务实现留在生成包的 `backend/business.*`、仓储和状态规则中。SDK 不认识具体项目和业务字段。共享前端放在 `frontend/`，由平台受控安装；服务不能在远程返回中夹带可执行网页。

## 2. 远程模块必须交付的内容

| 内容 | 标准 |
| --- | --- |
| `manifest.json` | 稳定模块与能力编号、版本、输入输出、角色基线和两端呈现；新服务使用 manifest 1.2 |
| `registration.json` | registration v1；所有要求的字段都提供，没有数据或流程时明确填空数组 |
| 权限附件 | 有正式业务对象时使用 access v1，覆盖全部能力；不能用连接凭据替代用户授权 |
| 业务实现和绑定表 | 每项能力都有真实处理函数；不能只声明名称而未实现接口 |
| 共享页面/对话 | 使用同一能力和对象；所需组件、流程编号及版本必须登记 |
| 独立说明和测试 | 安装、配置、启动、存储、迁移、错误、权限和业务验收方法；不携带真实数据和密钥 |

`registration.json` 的完整字段是：

- `registration_version`、`module_id`、`module_version`：注册标准与模块身份，必须与能力清单一致。
- `permissions`：`platform_access` 时携带完整权限附件；`capability_roles` 只适合无公开正式对象的简单工具，附件必须为 null。
- `data_objects`：公开对象的编号、名称、说明、数据 Schema、实际支持的 list/read/create/update/delete 能力及范围字段；没有实现删除就不声明删除。
- `business_chains`：公开业务步骤的入口与能力顺序。用于说明和连接检查，当前不会自动连续执行。
- `host_requirements`：主框架需安装的 workflow 和 interaction 编号与版本。
- `workflow_operations`：实际实现的对象、文件或任务接口；必须与 SDK 分派表完全一致，按名称排序。

完整可运行示例是 Node 模板的 `backend/registration.json`。数据 Schema 描述该对象公开的结构，不能用于直接访问数据库。字段可读写范围和正式状态仍由业务接口实施；本轮没有新增通用字段级授权引擎。

## 3. 固定接口与双向握手

服务为以下路径统一验证私有 Bearer 凭据，验证发生在解析业务及执行前。

| 接口 | 功能 |
| --- | --- |
| `GET /platform/v1/manifest` | 提供能力清单 |
| `GET /platform/v1/registration` | 提供完整公开内容和接入要求 |
| `GET /platform/v1/health` | 返回明确健康状态 |
| `POST /platform/v1/handshake` | 主动核对平台提供的内容，返回逐项确认 |
| `POST /platform/v1/invoke` | 依据明确能力、版本、当前身份和合法输入执行业务 |
| `POST /platform/v1/workflow/{operation}` | 仅实现 registration 中登记的对象/文件/任务接口 |

握手过程：

1. 主框架读取两份声明，校验引用与权限；再检查接口拒绝无身份、错误身份和无效请求的行为。
2. 主框架发送完整声明、支持的协议列表、随机编号和内容摘要。
3. 模块 SDK 比较本地与平台提供的完整声明，确认平台支持所需协议，核对全部实际函数与输入输出 Schema。
4. 任何内容不一致都拒绝确认；完全一致才返回原随机编号、摘要和准确函数清单。
5. 平台检查回应及自身安装依赖，保存报告。全部通过后，管理员才能发布模块。

模块不是原样回显随机编号就算通过。SDK 必须先完成本地检查。随机编号只绑定当前交换，不是业务授权票据；内容摘要由平台计算，模块通过比较完整 JSON 核实内容，避免不同语言对浮点数的序列化差异。

## 4. Node 模块使用

使用 Node 24，在平台根生成新目录，不能覆盖已有目录：

```powershell
.\.venv\Scripts\python.exe scripts/module_kit.py scaffold --help
.\.venv\Scripts\python.exe scripts/module_kit.py scaffold --template workflow-node --module-id example.review --title "审核示例" --output ..\work\example-review
.\.venv\Scripts\python.exe scripts/module_kit.py check <模块目录>
```

生成器复制业务模板、SDK、公开声明和测试。`createModuleServer` 接收 `{manifest, registration, token, handlers, workflowHandlers}`。能力与对象请求直接通过这两张真实函数表分派；缺失、多余或非函数绑定会阻止服务启动。业务函数仍执行范围、作者、状态、版本和幂等检查。

在生成的模块目录运行 `node --test tests/workflow.test.mjs` 完成独立测试；配置下述服务端变量后运行 `node backend/server.mjs`。真实接入使用管理员配置的服务地址，不能把离线检查或独立测试结果当成平台注册成功。

参考模板读取 `PLATFORM_SERVICE_TOKEN`、`PLATFORM_ACCESS_DECISION_URL`、`MODULE_PROJECTS_FILE` 和 `SERVICE_DATA_DIR`。前者是私有连接凭据；后两者是模块自己的合成项目配置和运行目录。真实值通过服务端配置提供，不能写入前端或交付包。

Node SDK 仅支持模板使用的封闭 Schema 子集；不认识的关键字会拒绝启动。需要完整 JSON Schema 时先替换验证器并补测试。参考业务输入限制为 64 KiB，包含完整声明的握手包单独限制为 1 MiB；较大服务须明确调整和测试限额，不能静默截断。SQLite 示例只支持单进程，不代表分布式事务。

## 5. 已有 Python 服务使用

保留原业务与数据库，复制 `sdk/python/registration.py` 和授权客户端；依赖 `jsonschema`。构造注册确认器：

```python
registration = Registration(manifest, document, actual_handlers, workflow_handlers)
# 业务请求通过 registration.handlers / workflow_handlers 的只读表分派
# authenticated GET /registration 返回 registration.document
# authenticated POST /handshake 调用 registration.confirm(request_json)
# RegistrationError 映射为 422，使用固定错误文字，不回显请求正文
```

`actual_handlers` 必须是实际请求使用的函数表。HTTP 适配器还负责固定路由、Bearer 验证、正文限额、超时、合法业务包络、输入输出校验以及中央权限请求。不能把注册确认器当成完整 HTTP 服务器或业务授权器。Python 对接的合成传输验证与 Node 完整服务验证分开记录。

进程内 `tool-python` 通过受控安装及离线校验加载，不是远程微服务，不进行 HTTP 握手。它仍须符合能力、权限、两端组件和实际业务验收规则。

## 6. 测试和升级要求

先运行生成包独立测试及离线 check，再在平台完成七项接入检查。继续检查真实业务：无授权、超范围、撤权、同版本并发、重复请求、重启恢复、页面和对话同事项办理、刷新及分支。接入报告不能代替这些测试。

声明或接口升级后同步模块版本、注册附件和测试，重新发现并验收；运行配置改变后旧验收失效。旧 SDK 不会自动更新，必须随模块显式发布。示例不包含真实模型、外部业务数据库或生产单点登录。

# 跨模块来源读取

独立模块若需重新核验固定上游对象，可使用可选 [source-reads 1.0](../contracts/access/v1/source-reads.md) 和同批 Python/Node server-only SDK。目标凭据不能跨模块转发，源对象 reader 必须登记并实际检查自己的权限和范围。页面只传稳定引用与修订；正式业务的类别、状态、用途和字段映射仍由各模块的显式 adapter 处理。
